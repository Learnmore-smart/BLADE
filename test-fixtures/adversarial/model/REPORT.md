## Answers to the brief

1. **Real tensor drop / offsets**: dropping a real tensor (`enclave_router.weight`) does **not** corrupt other `data_offsets` — the data region is copied verbatim so kept tensors still read correctly — but it leaves an unreferenced gap that fails contiguous-coverage validation → **the whole file becomes unloadable under strict loaders** (HF safetensors `InvalidOffset`, BLA `validateSafetensorsBuffer`). It does not recompute or compact anything.
2. **Value-marker over-trigger**: yes — any `__metadata__` string value containing `enclave.delegation`, `[BLA `, `Decompilation Advisory`, `enclave_build_id`, or the canary GUID drops the key regardless of name. 6/9 legit keys lost.
3. **GGUF typed KVs**: all 13 types + nested/deep legit arrays skip correctly — **for valid types**. Unknown type → 0-byte skip → desync/hang.
4. **`general.*` preserved**: required keys survive; standard `general.description`/`general.license` with marker-ish legit values are dropped (over-trigger, non-fatal).
5. **Interleaved armor**: PASS — only armor keys drop; real keys, descriptors, weights intact.
6. **GGUF tensor-info**: BLA adds **KV records only** — never tensor-info records or data blobs (`trailingTensorSlice` verbatim, `tensorCount` unchanged). Scrubber's verbatim `rest` is correct *except* it never re-pads: dropping a KV that was part of the original file shifts tensor data off `general.alignment` (G-6b OFFSET-CORRUPT). Irony: `protectGgufBuffer` itself misaligns real files; scrubbing restores it.
7. **Malformed**: header-length lies, truncations, and big-endian markers → uncaught exceptions (PARSE-FAIL); truncated tail values → silently corrupt output; huge counts → unbounded CPU; deep nesting → stack overflow (no depth cap, unlike BLA's 64).
